# CasMobile

This folder is primarily a container for the top-level pieces of the application.
While you can remove some files and folders that this application does not use,
be sure to read below before deciding what can be deleted and what needs to be
kept in source control.

The following files are all needed to build and load the application.

 - `"app.json"` - The application descriptor which controls how the application is
   built and loaded.
 - `"app.js"` - The file that launches the application. This is primarily used to
   launch an instance of the `MyApp.Application` class.
 - `"index.html"` - The default web page for this application. This can be customized
   in `"app.json"`.
 - `"build.xml"` - The entry point for Sencha Cmd to access the generated build
   script. This file is a place where you can hook into these processes and tune
   them. See the comments in that file for more information.

These files can be ignored from source control as they are regenerated by the build
process.

 - `"build"` - This folder contain the output of the build. The generated CSS file,
   consolidated resources and concatenated JavaScript file are all stored in this
   folder.
 - `"bootstrap.*"` - These files are generated by the build and watch commands to
   enable the application to load in "development mode".

## Android Build and Release

Use this procedure to create a release APK. It builds the Sencha production web
assets first, copies those assets into Cordova, then creates a signed Android APK.

### Prerequisites

- Sencha Cmd must be available on `PATH`.
- Node.js, Cordova CLI, Java JDK 17, and Android SDK must be installed.
- `ANDROID_HOME` must point to the Android SDK directory.
- The signing keystore and `cordova/build.json` must already exist locally. Do not
  copy passwords, keys, or other signing credentials into documentation or source
  control.

### Versioning

Before every release, increment both version definitions together:

- `app.json`: application `version`
- `cordova/config.xml`: widget `version` and `android-versionCode`

Use a unique, increasing `android-versionCode`; Android will reject an update with
the same or a lower value than an installed release.

### Standard release commands (PowerShell)

Run from the repository root:

```powershell
sencha app build production

robocopy build\production\CasMobile cordova\www /E /R:2 /W:1
if ($LASTEXITCODE -ge 8) { throw "Web asset copy failed: $LASTEXITCODE" }

Push-Location cordova
cordova build android --release --buildConfig=build.json
Pop-Location
```

`robocopy` exit codes from 0 through 7 are successful outcomes; only 8 or higher
indicates a copy failure.

The signed APK is produced at:

```text
cordova/platforms/android/app/build/outputs/apk/release/CprMobile.apk
```

Copy it to `release/CprMobile_v<version>.apk`. Verify the version from
`output-metadata.json`, and verify Android signing with `apksigner`:

```powershell
& "$env:ANDROID_HOME\build-tools\<build-tools-version>\apksigner.bat" verify --verbose `
  cordova\platforms\android\app\build\outputs\apk\release\CprMobile.apk
```

### Recovery for a failed Android build

The Android build can fail with messages such as `Unable to delete directory` when
a previous Gradle daemon holds generated files, or when stale generated folders are
read-only. Do not retry repeatedly without cleanup.

1. Stop Gradle daemons:

   ```powershell
   Push-Location cordova\platforms\android
   .\gradlew.bat --stop
   Pop-Location
   ```

2. Remove only generated build directories, then rerun the standard release commands:

   ```powershell
   attrib -R cordova\platforms\android\app\build /S /D
   attrib -R cordova\platforms\android\CordovaLib\build /S /D
   Remove-Item cordova\platforms\android\app\build -Recurse -Force
   Remove-Item cordova\platforms\android\CordovaLib\build -Recurse -Force
   ```

   These directories are Gradle-generated caches and are recreated by Cordova. Do
   not delete `cordova/platforms/android/app/src`, the signing keystore, or other
   project source/configuration files.

3. If the build reports `EPERM` while reading `ANDROID_HOME`, confirm that the
   account running Cordova has read access to the Android SDK, then rerun the build.

## Basic Application Structure

Applications that target a single toolkit will have the following structure.

    app/                # Contains JavaScript and Theme code
        model/          # Data model classes
        view/           # Views as well as ViewModels and ViewControllers
        store/          # Data stores
        controller/     # Global / application-level controllers

    overrides/          # JavaScript code that is automatically required

    resources/          # Assets such as images, fonts, etc.

### app/

This folder contains JavaScript (.js files) and styling (.scss files) common
for all builds of the application.

#### app/controller/

This folder contains the application's global controllers. ViewControllers are located
alongside their respective view class in `"./view"`. These controllers are used for routing
and other activities that span all views.

#### app/model/

This folder contains the application's (data) Model classes.

#### app/view/

This folder contains the views as well as ViewModels and ViewControllers depending on the
application's architecture. Pure MVC applications may not have ViewModels, for example. For
MVCVM applications or MVC applications that use ViewControllers, the following directory
structure is recommended:

    app/view/
        foo/                    # Some meaningful grouping of one or more views
            Foo.js              # The view class
            Foo.scss            # The view class styling
            FooController.js    # The controller for Foo (a ViewController)
            FooModel.js         # The ViewModel for Foo

This structure helps keep these closely related classes together and easily identifiable in
most tabbed IDE's or text editors.

#### app/store/

This folder contains any number of store instances or types that can then be reused in the
application.

## Overrides

The contents of "overrides" folders are automatically required and included in
builds. These should not be explicitly mentioned in "requires" or "uses" in code.
This area is intended for overrides like these:

    Ext.define('CasMobile.overrides.foo.Bar', {
        override: 'Ext.foo.Bar',
        ...
    });

Such overrides, while automatically required, will only be included if their target
class ("Ext.foo.Bar" in this case) is also required. This simplifies applying
patches or extensions to other classes.
